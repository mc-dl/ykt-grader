# 架构与设计取舍

## 1. 分层

```
┌──────────────────────────────────────────────────────────┐
│ 人 / Agent                                               │
│   读题、看作业、判断对错、写评语、定分                    │
└───────────────▲──────────────────────────┬───────────────┘
                │ results.json             │ 读文件
┌───────────────┴──────────────────────────▼───────────────┐
│ 脚本层 (scripts/*.mjs)                                    │
│   harvest → 附件落盘     submit → 评语/分数写回           │
│   verify  → 读回核验     roster/report → 统计             │
└───────────────▲──────────────────────────┬───────────────┘
                │ CDP (127.0.0.1:9222)     │ DOM
┌───────────────┴──────────────────────────▼───────────────┐
│ 用户自己的 Chrome（已登录雨课堂）                          │
└──────────────────────────────────────────────────────────┘
```

三层职责边界：

- **Chrome 负责认证与渲染**。脚本不碰账号、密码、Cookie；登录失效时脚本只会失败，不会尝试"恢复登录"。
- **脚本负责搬运与核验**。它不知道答案，也不决定分数；它只保证"抓对了人、写对了人、写进去了"。
- **Agent/人负责判断**。评分、评语、是否提交由使用者授权与决定。

## 2. 为什么用 CDP，不用无头浏览器

| 方案 | 优点 | 问题 |
|---|---|---|
| 无头浏览器 + 自动登录 | 全自动 | 需要保存密码/Cookie，验证码与风控不可控，泄露风险高 |
| 独立 Playwright 配置 | 干净 | 每次都要重新登录，附件下载与 PDF 查看器行为可能不同 |
| **附着用户 Chrome（CDP）** | 复用真实登录态与真实渲染 | 需要用户手动启动调试端口；页面可见，操作"半自动" |

选择 CDP 的理由是**责任边界清晰**：认证归用户，搬运归脚本。代价是不能无人值守，但这本来也不该无人值守。

## 3. 为什么把"抓附件"和"写成绩"拆开

一次批改的瓶颈不是点击，而是**读图与判断**。把流程拆成两段：

```
串行：harvest（浏览器只能一次处理一个学生）
  ↓
并行：读图 / 对答案（可以多个 Agent、多线程）
  ↓
串行：submit（写回必须一次一个，且要核对身份）
```

好处：

- 浏览器操作与判断解耦，读图慢不会拖住页面；页面刷新也不会丢掉已读结果；
- 附件落盘后可反复查看、复核、补充评语，不必重新进网页；
- 写回阶段可以按 `sid` 精确重放，失败只补失败的那几条。

## 4. 关键设计决定

### 4.1 分数用输入框写，不用按钮

按钮是文本匹配，`getByRole('button', {name:'9'})` 会命中 `9` 和 `9.5`（子串匹配），历史批次因此多给过 0.5 分。现在优先 `.score-panel input` + `Enter`；只有找不到输入框才退回按钮。

### 4.2 写前核对 `sid`，写后核对批改率

页面在"极速打分"下会自动换人，任何"点完就继续"的写法都可能写错对象。脚本在点击卡片后重新读取 `.student-item.active`，不含目标 `sid` 就抛错中止。写完后同时看"批改成功"提示与批改率，二者都不变就记为未确认。

### 4.3 日志即状态

- `manifest.json`：已抓过谁、抓到了什么形态；
- `*.submitted.json`：谁成功、谁失败、当时的批改率；
- `roster.json`：最终名单与分数。

全部是可读 JSON，不依赖数据库。中断后重跑，脚本据此跳过已完成项。**日志里的 `ok: true` 只代表"页面给了成功信号"，最终仍以网页为准。**

### 4.4 选择器集中、可诊断

DOM 选择器散落在各脚本中，但每个都可能失效。因此提供 `pdfinfo.mjs`（结构诊断）和 `status.mjs`（页面诊断），页面改版时先看真实 DOM 再改，而不是猜。

## 5. 并行读图的边界

历史批次用过"16 路 subagent 并行读图 + 主 Agent 串行写回"。这套模式可复用，但有前提：

- 每个读图任务**只读本地附件**，不碰浏览器；
- 输出固定 JSON（`sid`、分数、错题、评语），主 Agent 负责合并与去重；
- 并发上限按机器与 API 限额调整，不要同时开几十个；
- 写回始终串行，且写回前重新核对学生身份。

并行只加速"看"，不加速"判断质量"。读图 Agent 也必须看到全部页面。

## 6. 已知失效点

| 失效点 | 表现 | 处理 |
|---|---|---|
| 页面改版 | 找不到 `.student-item` / 分数输入框 | `pdfinfo.mjs` 看 DOM，改选择器，小样本验证 |
| 登录过期 | 跳转登录页，正文为空 | 让用户重新登录，不要自动填表 |
| 弹层遮挡 | 点击学生卡片无反应 | 关闭题干/批注弹窗；脚本会隐藏 `.dialog-problem` |
| PDF 不出画布 | `harvest` 记为 `iframe` 或无附件 | `dlpdf.mjs` 下载 + `pdfrender.py` 渲染 |
| 列表虚拟滚动 | 只读到前几十人 | `collectAllStudents` 已滚动加载；仍不全就增大滚动次数 |
| 网络慢 | 切人后内容没加载完 | 增大 `waitForTimeout`，或先读批改率确认页面稳定 |

## 7. 不做什么

- 不提供自动判分模型：分数必须能追溯到具体题号与依据；
- 不绕过登录、验证码、风控；
- 不调用非公开接口抓附件；
- 不做"一键给所有人 10 分"这类批量操作；
- 不在仓库里保存任何学生数据。
